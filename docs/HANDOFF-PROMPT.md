# 上下文交接模板（Handoff Prompt）

当前对话快用完时，用下面的模板把任务完整交给**新建任务**。
新建任务看不到本对话的任何内容 —— 模板的价值就在于把所有必要上下文写成自包含的。

---

## 怎么用

1. 复制下面的模板
2. 把 `<...>` 占位处填上（**填不出来的就留着，并标注"需自行确认"** —— 让下一个 AI 去查，比编一个错的强）
3. 粘贴到新任务，发送
4. 新任务开工前会先读 `docs/ARCHITECTURE.md` 和 `.workbuddy-ai/memory/`，这两处是长期事实的载体，不用在提示词里重复

> 模板里**不要**粘贴大段代码或日志 —— 写清文件路径和现象即可，让下一个 AI 自己读。
> 提示词越短、越指向文件，交接越可靠。

---

## 模板（复制这一段）

```
【任务交接】WorkBuddy 换肤插件（anonbuddy-skin）

项目路径：D:\anonbuddy-skin

## 请先读这些（按顺序，不要跳过）

1. docs/ARCHITECTURE.md —— 架构、改动→测试映射表、别改坏的不变量、写测试的规矩
2. .workbuddy-ai/memory/MEMORY.md —— 项目长期约定（含大量踩坑记录）
3. .workbuddy-ai/memory/ 下最近 2~3 天的日志 —— 最近做了什么、什么坏了、怎么修的

## 当前状态

- 上一轮已经完成：<一句话概括，例如"把皮肤 CSS 从模板字符串外置到 src/css/skin.css 并统一了测试入口">
- 最后一轮验证结果：`npm test` = <例如 "9/9 PASS">，`npm run test:all` = <例如 "14/14 PASS">
- 工作区是否干净：<例如 "有未提交改动，未 commit">

## 本次要做的

<清晰的目标。一句话说"做什么"和"做完怎么算成功">

例：
> 把插件做成可以一键安装的 npm 包，别人 `npx anonbuddy-skin apply` 就能用。

## 验收标准

- [ ] <可验证的条目 1>
- [ ] <可验证的条目 2>
- [ ] `npm run test:all` 全绿
- [ ] 状态中性：跑完测试后界面与测试前一致（主题、localStorage、图标位置）

## 已知的坑 / 约束（重要）

- <例如 "这个改动会碰到注入脚本，注释里严禁出现反引号，改完必须先 npm run lint">
- <例如 "别改 applySkin 的幂等收尾逻辑，test-reapply-idempotent 会挂">
- <如果上一轮有未解决的问题，写在这里>

## 注意

- 改动前先看 docs/ARCHITECTURE.md 的「改动 → 该跑哪些测试」表，不要无脑跑全量 e2e
- .ps1 必须纯 ASCII
- e2e 依赖真实运行的 WorkBuddy；如果没在跑，先说一声再决定要不要启动
```

## 几种常见场景的填空示例

### 场景 A：继续做功能

```
## 当前状态
- 上一轮已完成：CSS 外置 + 统一测试入口（24 个测试文件 → 一个 runner）
- 最后验证：npm test = 9/9 PASS；npm run test:all = 14/14 PASS
- 工作区：有未提交改动

## 本次要做的
给 🎨 菜单加"导入/导出主题包"功能：能把自定义主题导出成 .json 分享，也能导入别人的。

## 验收标准
- [ ] 菜单里有导出按钮，导出文件能重新导入且还原一致
- [ ] 导入失败（格式错/图片超大）有明确提示，不崩
- [ ] 新增 e2e 用例覆盖"导出→导入"往返一致
- [ ] npm run test:all 全绿

## 已知的坑
- 导出/导入涉及 localStorage 里的 dataURL，注意体积（现在单主题 base64 可能几百 KB）
- 菜单是注入脚本生成的，改 src/skin-menu.mjs 后必须先 npm run lint
```

### 场景 B：修 bug

```
## 当前状态
- 上一轮已完成：<...>
- 工作区：干净

## 本次要做的
修 bug：<现象描述>。复现步骤：<1. 2. 3.>。期望：<...>，实际：<...>

## 验收标准
- [ ] 按复现步骤操作后行为正确
- [ ] 加一个回归测试，先把 bug 固定住（测试应该先 FAIL 再 PASS）
- [ ] npm run test:all 全绿

## 已知的坑
- 先用差分定位法确认是不是皮肤造成的：pause → 快照 → apply → 快照 → diff
  （见 docs/ARCHITECTURE.md「诊断手法」）
```

### 场景 C：发版 / 整理仓库

```
## 当前状态
- 功能已完备，最后验证：npm run test:all = 14/14 PASS

## 本次要做的
把仓库整理成可以公开到 GitHub 的状态，并写好 README 的英文版。

## 验收标准
- [ ] git status 干净，无遗留大文件（outputs/ 等已在 .gitignore）
- [ ] 别人 clone 后不装任何额外东西、不改任何文件就能跑通 npm test
- [ ] README 英文版与中文版信息一致
- [ ] 首次提交流程走通（git add/commit/push）

## 已知的坑
- 本仓库历史上出现过 themes-removed/ 被跟踪、outputs/ 19M 入库的问题，注意别复发
```

## 为什么这样写有效

| 做法 | 原因 |
|---|---|
| 指向 `docs/ARCHITECTURE.md` 而不是贴内容 | 文档会随代码更新，粘贴的快照会过期 |
| 明确"上一轮完成到哪" | 新任务无法从代码看出哪些是刚改的 |
| 给可勾选的验收标准 | 把"做完了"从主观判断变成可验证条件 |
| 写清已知的坑 | 避免同一个坑踩第二次（这个项目坑特别多） |
| 提醒先看测试映射表 | 避免无脑跑全量 e2e，这正是上一轮要解决的问题 |
| 不贴大段代码/日志 | 上下文是稀缺资源，路径比内容更高效 |
